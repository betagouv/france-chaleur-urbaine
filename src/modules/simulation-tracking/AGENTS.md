# simulation-tracking module

First-party tracking of the renewable heating simulations (`chaleur-renouvelable` journey): one mutable row per arrival on the results page, written only by public client beacons, with its start page, current inputs, offered contact options and outcome, plus the admin flow view. Sibling of `conversion-tracking` (which measures the classic journey: displays → address tests → demands) and reuses its anti-abuse primitives.

> Product documentation (French): `/admin/doc/chaleur-renouvelable`, section « Le suivi des simulations ». Update `src/modules/doc/content/chaleur-renouvelable.mdx` and run `pnpm doc:build-search-index` for any behavior change.

## Structure

- `constants.ts` — outcomes, Zod schemas of the beacons (`zCreateSimulation`, `zUpdateSimulation`, `zRecordSimulationOutcome` built on `zSimulationOutcomeDeclaration`) and of the admin funnel (`zGetSimulationFunnel`); snapshot / start types.
- `server/service.ts` — create (idempotent on the client id), update (bounded), record outcome (first wins), `getSimulationFunnel` (grouped rows for the admin view).
- `server/trpc-routes.ts` — router `simulationTracking`.
- `client/useSimulationTracking.ts` — `useStartSimulation()` (form pages: stores the start page in a Jotai atom right before the client-side navigation), `useSimulationTracking()` (results page: `track(snapshot)` creates, updates, or chains a new simulation when the address or building changes, and exposes the current `simulationId`), `useSimulationStartRoute()` (results page back link: `/` → home in comparator mode, otherwise the landing), `useRecordSimulationOutcome()` (demand form, France Rénov' callout). Fire-and-forget, `/admin` excluded.
- `client/simulation-funnel.ts` — pure builders: Sankey nodes/links, indicators, and `FUNNEL_LEGEND` (single source of every column value, its label, color and meaning).
- `client/SimulationsSankey.tsx` — Recharts Sankey with wide nodes carrying their label and volume inside (volume folded on the last line when the node is short, label beside the node when it is shorter still), share labels on links, custom tooltip (the Recharts one flickers on Sankey links), node sorting left to Recharts to minimize crossings. share labels at the start of their link, 1100 px minimum width with horizontal scroll below, height grows with the fullest column and so that the smallest node holds two lines, up to a ceiling.
- `client/SimulationsFunnelHelpDialog.tsx` — self-documentation dialog built from `FUNNEL_LEGEND`.
- `client/SimulationsConversionPage.tsx` — `/admin/conversion/chaleur-renouvelable` (nuqs filters, indicators, flow).

## Model

- **Identity**: one simulation per building shown on the results page, or per address when no building is known (the typed address is corrected to the building's own address once it is confirmed: not a change). Its uuid is generated by the client, kept in React state only — never in the URL nor in browser storage, so no tracker and no consent. Changing the building (or the address, when no building is known) starts a new simulation chained to the previous one (`previous_simulation_id`, same start page); a reload or a shared link is a new simulation, counted as a direct arrival. The uuid is also the write secret of the later updates.
- **Start page**: `route` / `page` of the page whose form was submitted (`/`, `/chaleur-renouvelable`) plus the conversion-tracking attribution of its URL (`source`, `host`); results page itself on a direct arrival. Handed over through the atom, read when the results page mounts and released when it unmounts (a page left before its simulation is created leaks nothing); the back link of the results page reads it too. `refusal_already_known` (arrival from the « connection not feasible » email) overrides the entry in the admin view.
- **Snapshot**: inputs (housing type, radiators, outdoor space, address, building, commune, department), `address_resolved` (the BAN matched a house number; an unrecognized address, e.g. a street without number, is still a simulation, computed without building nor eligibility) and what was offered (`heat_network_available`, `ccrt_demand_available`, `recommended_solution`, null when no solution fits). Created once the results are ready (`router.isReady` on this statically optimized page, eligibility loaded, building confirmed, prefill done), then **updated on every change of the other parameters**: the current state is what counts, `revisions` counts the edits (an address or building change is a new simulation, see Identity).
- **Outcome**: declared by the client after the server confirmed the demand (`heat_network_demand`, `ccrt_demand`; a deduplicated classic demand records nothing) or on the France Rénov' appointment click (`france_renov_orientation`). A demand outcome carries `demand_id` (the created `demands` or `demands_chaleur_renouvelable` row): the only link to the demand tables, for reconciliation. First outcome wins. Demand creation is never touched: a closed tab between the two leaves a simulation without outcome, the demand tables stay the truth.
- **Bounds of the public write endpoints**: `ON CONFLICT DO NOTHING` on create, updates and outcomes only within `fcrSimulationUpdateWindowHours` and under `fcrSimulationMaxRevisions` (business rules), crawlers dropped, rate limit 60/min.
- **Anti-abuse**: columns `ip` / `user_agent` / `excluded` shared with `conversion_events`: `getTrackingRequestContext` and `mostSpecificRuleExcludes` from `conversion-tracking`, IP rules reconciliation, the abuse detection (`getSuspiciousIps` counts the simulations per IP, threshold on tests + simulations) and the purge cron (`purgeOldConversionEventIps`) cover this table too; the purge also nulls `address` and `batiment_construction_id` (indirectly identifying, kept for debugging only, never displayed). Excluded rows are never counted.
- **Admin funnel**: `getFunnel` groups the period by start page × offered options × whether a solution fitted × outcome, with input filters; the client derives the six proposed contacts (heat network + CCRT, heat network + France Rénov', CCRT, France Rénov' with alternatives, France Rénov' without any solution, France Rénov' on an unrecognized address), the four outcomes (including « sans suite ») and the indicators (each demand rate against the simulations where that demand was offered). Page displays stay on `/admin/conversion`.

## tRPC Routes (`simulationTracking`)

| Procedure | Type | Auth | Description |
| --- | --- | --- | --- |
| `create` | mutation | public (rate-limited 60/min) | Creates a tracked simulation (client uuid, start page, snapshot); replays ignored, crawlers dropped. |
| `update` | mutation | public (rate-limited 60/min) | Replaces the snapshot and counts a revision, within the update window and revisions cap. |
| `recordOutcome` | mutation | public (rate-limited 60/min) | Records the first outcome of a simulation; a demand outcome carries the created demand id. |
| `getFunnel` | query | admin | Simulations of a period grouped for the flow view; excluded rows ignored. |

## Owned table

`simulations_chaleur_renouvelable` (migration `20261029120000`): identity and timestamps, `previous_simulation_id`, `revisions`, start page (`route`, `page`, `source`, `host`), snapshot columns, `outcome` (CHECK) / `outcome_at` / `demand_id`, anti-abuse columns. Indexes on `created_at` and a partial purge index. Registered in the `fcu` bootstrap bundle and in `cleanDatabase()`. The only indirectly identifying data are the address and the building id, both purged with the IP: never add contact fields here.

## Dependencies and boundaries

- Imports `@/modules/chaleur-renouvelable/constants` **only** (value lists of the simulator inputs) — never its `client/` or `server/`. The simulator and the home page import this module's client hooks: the cycle is confined to `constants.ts` on purpose.
- Depends on `conversion-tracking` (request context, exclusion rule, client `trackingContext` helpers), `trpc`, `app/business-rules`, Recharts and Jotai.
- Does not create or read demands, does not emit PostHog events (the `analytics` module keeps its own), does not count page displays.

## Usage

```ts
// Form page, right before navigating to the results page
const startSimulation = useStartSimulation();
startSimulation();
// Results page (inside useChoixChauffageResults)
const simulationTracking = useSimulationTracking();
simulationTracking.track(snapshot); // creates, updates, or chains a new simulation on an address change
// After a demand is created, or on the France Rénov' click
const recordSimulationOutcome = useRecordSimulationOutcome();
recordSimulationOutcome(simulationId, { demandId: createdDemand.id, outcome: 'ccrt_demand' });
```
