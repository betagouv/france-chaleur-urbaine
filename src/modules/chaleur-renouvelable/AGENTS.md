# chaleur-renouvelable module

Renewable heating guidance journey: collect building/context inputs, rank heating modes, create either a classic connection demand or a dedicated CCRT accompaniment demand, and expose admin/CCRT follow-up views.

> Product documentation (French, product-team audience): `/admin/doc/chaleur-renouvelable`, with cross-effects documented in `/admin/doc/cycle-de-vie-demande` when this module creates or changes classic connection demands. Update `src/modules/doc/content/*.mdx` and run `pnpm doc:build-search-index` for any behavior change.

Unknown distances exclude the heat-network flow.
- **Geothermal coverage**: house and collective geothermal heat pumps require at least one favorable GMI zoning (nappe or sondes) and either `couv_sondes_200_2025` strictly above `businessRules.fcrGeothermalMinCoveragePercent.value` or `place_nappe === true`. The two OR groups are intentionally independent; do not pair zoning and resource criteria by technique. A red zoning does not veto the other favorable zoning. Preserve the historical French resource prerequisite label and BRGM source; the space prerequisite must mention both probes and wells, also with BRGM as its source. Keep incompatibilities and prerequisites aligned with these alternatives. `hasGeothermalProbeSpace` is the historical name for `place_nappe`, which describes room for two groundwater wells, not probes. The aquifer potential (`pot_nappe`) stays in the database and import but is not exposed to the simulator or used for eligibility or prerequisites. Use the existing `couv_sondes_200_2025` percentage column, already populated by the BatEnR import; no additional column or migration is needed.

## Main Flows

- **Google Ads / acquisition**: `useChoixChauffageResults` emits `multienr_simulation_completed` only after results are ready; `DemandFCRForm` emits `multienr_accompaniment_submitted` only after the server confirms a new CCRT or classic demand (`demand_type=ccrt|heat_network`). Explicit `google_ads` consent and validated GTM configuration are mandatory; failures, missing coverage, classic duplicates and France Rénov clicks do not count as demand conversions. Shared UTM source/medium/campaign attribution is retained in memory across internal navigation and passed through `zDemandeChaleurRenouvelable.acquisition`. The server stores it only in the `acquisition` column of the corresponding demand table (admin origin column, query/search/export only); duplicate classic demands keep their original attribution.

- **CCRT public coverage**: `getAddressEligibilityContext` exposes only `isCcrtCovered`, never account details. The result page combines it with collective housing eligibility; uncovered alternative-heating/refusal paths display France Rénov'. The server rechecks coverage before dedicated creation, and a missing id without a classic submission result redirects the form to France Rénov' without displaying a success confirmation. Classic connection demands remain available regardless of CCRT coverage.
- **Result page state**: query params are parsed/serialized by `useChoixChauffageQueryParams`; avoid adding local state that can drift from the URL.
- **Building selection**: BAN/RNB/BDNB/BatEnR logic is in `getBatEnrBatimentsSelectionContextByBanId`; multiple candidates trigger the client selector. After confirmation, `client/building-address.ts` resolves the recorded building address to a unique precise BAN match; `useChoixChauffageResults` updates the URL and BAN feature together, cancels stale corrections, and retains the input on missing/ambiguous matches. Explicit construction IDs remain selected even when the corrected address has a different candidate list.
- **Classic demand**: `createDemandeChaleurRenouvelable` first calls the classic demand path when the heat network is eligible and the user has not selected the public-advisor/refusal path. It reuses `@/modules/demands/server/creation-user` and patches FCR snapshot fields into `legacy_values`.
- **Dedicated CCRT demand**: when no classic demand is created, `createCcrtDemand` creates an unvalidated `demands_chaleur_renouvelable` row for `immeuble_chauffage_collectif`. The server resolves geographic scopes for classic permissions and requires territorial coverage by an active CCRT account before writing or sending confirmation. Admin validation publishes it to the CCRT workspace and sends the CCRT notification email only when automated CCRT emails are enabled.
- **Refusal follow-up link**: `originDemandId` and `adresse` come from the “Raccordement non réalisable” email URL. On results, `originDemandId` suppresses the heat-network solution from compatible/recommended results, shows it as incompatible with a refusal reason, and bypasses classic demand creation; it is validated against an existing non-deleted `demands` row with status `Non réalisable` and the same email before being stored as `demands_chaleur_renouvelable.origin_demand_id`.
- **CCRT permissions**: The list and all actions share `server/ccrt-access.ts`: admin or CCRT accounts with a matching commune/EPCI/EPT/department/region permission, or a `custom_territory` permission matching the demand's `custom_territory_ids` (see `src/modules/custom-territories/AGENTS.md`); non-admins only see validated demands. Network/organization permissions do not apply because CCRT demands have no assigned network. The page and routes use the CCRT role group (`renewableHeatAccessRoute` for tRPC), and service filters also reject other non-admin roles. The access-holder list displays active CCRT accounts with matching territorial permissions only (including prospective access before publication for admins, with their last connection dates); admins retain their workspace access; gestionnaire, collectivite and alec accounts have no access even with matching territorial permissions. Admins manage permissions using the existing user editor.
- **CCRT territories**: `getCcrtTerritory` uses address coordinates against `ign_communes`, like classic demands, falling back to the exact city code if no spatial match exists. Municipal arrondissement codes must resolve to the parent commune before resolving EPT membership. IGN's Grand Paris `EPCI/EPT` values are split so `epci_code` contains only the EPCI; EPT comes from `ept.membres`. Public coverage, creation and building corrections must all pass coordinates. The returned territory also carries `custom_territory_ids` (`resolveCustomTerritoryIds`), so every write of the territory codes keeps the custom territories in sync.
- **CCRT emails**: active CCRT account creation sends an opening email (`users/server/service.ts`). New-demand notifications and pending-demand reminders run on their scheduled crons according to recipient preferences and territorial permissions. Previously unnotified validated demands are picked up on the next eligible daily/weekly run; opening emails skipped during the temporary suspension are not replayed.
- **CCRT notifications and reminders**: `server/ccrt-notifications.ts` mirrors `demands/server/manager-notifications.ts` for `demands_chaleur_renouvelable`: `notifyCcrtOfNewDemands` (cron, weekdays 10:10) matches active `ccrt` accounts to validated demands through the territorial permissions in SQL (commune/EPCI/EPT/department/region/custom territory; the role is filtered, other territorial roles never receive these emails), honours `preferences.notifications.new_demands` (daily: one detailed email per demand; weekly: Monday digest of the demands marked since the previous Monday; none), sets `notified_at` only when at least one recipient exists (event `ccrt_demand_notification_sent`, PostHog `ccrt_demandes:demande_received` per recipient and demand). `notifyCcrtOfUnhandledDemands` (cron, Tuesday 9:50) reminds opted-in accounts (`pending_demands_reminder`) of demands still « À traiter » more than `unhandledDemandReminderDays` after reception (notification day, or the Monday digest for weekly accounts), listing the `ccrtReminderListedDemands` oldest ones. Admin validation only publishes the demand; it never sends emails. Assignment candidates remain CCRT-only and never grant access.
- **Follow-up status**: `Installation réalisée` belongs to the `completed` / « Réalisées » tab. The former project-state field is no longer accepted by update APIs or included in exports; preserve its stored values and historical events.
- **Simulation tracking**: `useChoixChauffageResults` hands its snapshot (inputs, `isHeatNetworkEligible`, `isCcrtDemandEligible`, recommended solution) to `useSimulationTracking().track` once the results are ready (`router.isReady`, eligibility loaded, building confirmed, prefill done): the simulation is created, updated, or chained to a new one when the address or building changes; `DemandFCRForm` records the outcome of a demand actually created, `FranceRenovAdvisorCallout` the appointment click; `ChoixChauffageForm` marks the landing page as the start page before navigating. Model, bounds and routes: `src/modules/simulation-tracking/AGENTS.md`. Demand creation is never touched by the tracking.

## Data Ownership

- Owns `demands_chaleur_renouvelable`, `ccrt_demand_notes`, and `ccrt_demand_emails`. The tracked simulations table belongs to `simulation-tracking`.
- `zCcrtBuilding` accepts only editable building/heating/refusal fields. `zCcrtIdentification` separately accepts co-ownership and applicant details. Address, original comments and declared project stages remain server-owned and are never rewritten from either correction payload.
- `server/ccrt-building.ts` recalculates corrections with the shared simulator selectors, refreshes territories and result URL, and uses `updated_at` for optimistic concurrency. Never trust client-provided ranking or territory codes. Public submission and building correction share `getAlternativeHeatingSolutionLabels` to retain at most three alternatives, excluding the dedicated heat-network result.
- `server/ccrt-demand-update.ts` applies status changes and optional note insertion under one demand lock, shared by admin, CCRT and successful email sends. Historical assignments and project states remain unchanged. Its committed changes drive audit and CCRT tracking; notes and unchanged follow-up never renew the building concurrency token. `client/ccrt-demand-cache.ts` centralizes invalidation of shared views after mutations.
- `server/ccrt-notes.ts`, `ccrt-emails.ts`, and `ccrt-follow-up.ts` implement append-only shared notes, idempotent SMTP reservations, and paginated audit. Events use context `ccrt_demand` and the mutation transaction. Successful emails optionally move a still-to-process demand to first contact; failed or pending sends never appear as successful history. A pending reservation after ambiguous SMTP/persistence failure requires manual reconciliation before any retry.
- CCRT email composition reads `users.getPreferences`; successful sends save `email_signature` through `updateUserPreferences` in the email transaction, preserving notification settings and emitting the shared preference audit event.
- Notes can only be added with `updateDemandeChaleurRenouvelable`; there are no standalone note create/update/delete routes. Historical note edit/delete events remain readable.
- `getFollowUp`, `updateBuilding`, `updateIdentification`, `sendEmail`, and `updateDemandeChaleurRenouvelable` recheck demand visibility server-side. The shared timeline only includes demand events and excludes private admin-comment events for non-admins; user permission updates and synchronizations are excluded.
- Reads `communes` to resolve the department for CCRT eligibility; the `geoAddress.context` string is not authoritative for creation.
- Reads `bdnb_batenr`, `bdnb_batiments`, `reseaux_de_chaleur`, `reseaux_de_froid`, `ign_communes`, France Rénov data, and the RNIC data.gouv tabular API for simulation/demand context.
- Creates/patches classic `demands` only through the demands module APIs; never write classic demand legacy blobs directly here except via existing helpers such as `mergeLegacyValues`.

## Gotchas

- `cleanDatabase()` clears `ign_*` geography tables and demand tables, but not the static `communes`/`departements` tables; use idempotent seed helpers for those.
- Public CCRT/France Rénov routing uses the front-only pilot departments and `housingType`; management and notifications use classic permissions, independently of the pilot list.
- A public-advisor/refusal path with a heat-network-eligible address deliberately bypasses classic demand creation and can create a CCRT demand when the address/building is in the experimentation scope. The same applies to result URLs carrying `originDemandId`.
- `originDemandId` is optional and must be treated as untrusted user input; keep validation server-side and do not lock a classic demand unless the stored link was validated.
- `demands_chaleur_renouvelable.project_state` is historical data; do not reset it when changing statuses.
- If you add or rename statuses/project states, update `constants.ts`, admin UI assumptions, doc inventories, and tests.
- If you touch a form in this module, load `src/modules/form/AGENTS.md`; `useAppForm` conventions are mandatory for new/edited forms.
- If you touch UI layout or Tailwind classes, load `.ai/context/styling.md` and check responsive text/button behavior.

## Admin demand origin

The admin list computes `origin` with the shared `analytics/demand-origin.ts` classifier and integration labels. Only admin responses include the acquisition snapshot and computed origin; professional projections omit both. The workspace has an admin-only origin column/popover, URL channel filter (`CcrtDemandOriginFilter`, from the column header on desktop and the mobile filter panel) and detailed export. The acquisition snapshot carries the FCU refusal-email indicator; `origin_demand_id` remains a business link, not an attribution fallback. Public capture stays in memory only. See `analytics/AGENTS.md` for storage, rules and pending privacy review.

## Reopening published demands

`server/ccrt-reopening.ts` provides the admin-only `reopenDemand` mutation. The admin list includes the latest status change authored by a current CCRT account; confirmation uses that snapshot and the mutation checks `updated_at` under the demand lock. A conflict refreshes the list before another confirmation. Reopening sets `validated = false` and the durable `reopened_at` marker without resetting follow-up, assignments, notes, emails or `notified_at`. Email reservations and reopening share the demand lock: reopening refuses a pending send, and a non-admin reservation rechecks publication under that lock before SMTP. The new-demand cron excludes every demand with `reopened_at`, including weekly digests and never-notified demands; ordinary reminders remain available after revalidation for previously notified demands. Archival, transfer and restoration retain this marker. Moderation counts represent current state, never accumulated actions. Archive reasons include `duplicate`. An explicit transfer `managerMessage` is appended to the classic demand comment with an FCU attribution; private admin comments remain in the original demand.

The admin access column reuses `demands/client/AccessCountsCell` and its dialog with supplied CCRT users, including last-connection dates. Supplying users disables the classic-demand permission query; dedicated CCRT access rules remain authoritative. Moderation emails are queued: local development requires a separate `pnpm cli jobs start` worker (or processing the specific job) in addition to `pnpm dev`.
